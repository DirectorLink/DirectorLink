# C4Bridge v0.1.0-alpha.4

Fixes the first Light V2 control bug found during real-system alpha.3 testing.

## What was wrong in alpha.3

The browser/API path worked and the command envelope reached Director, but C4Bridge used the wrong Light V2 target parameter:

```text
LIGHT_BRIGHTNESS_TARGET
```

That name belongs to the brightness-changing notification side of the Light V2 protocol. The `SET_BRIGHTNESS_TARGET` command requires a target expressed as percent, level, or preset ID.

## Fixed command mapping

C4Bridge now uses the documented Light V2 command parameters:

- `on` → `LIGHT_BRIGHTNESS_TARGET_PRESET_ID = 1`
- `off` → `LIGHT_BRIGHTNESS_TARGET_PRESET_ID = 2`
- `set_brightness` → `LIGHT_BRIGHTNESS_TARGET_PERCENT = 0..100` and `RATE = 0`

On/Off therefore follows the project's configured Light V2 static presets instead of forcing a hard-coded brightness.

## Better verification

The web app no longer treats HTTP 202 as proof that the physical light changed.

After a command, it polls `GET /v1/lights` for up to 5 seconds and only reports success when Director's Light V2 variables confirm the requested state.

If Director does not confirm the state, the UI reports that the command was sent but not confirmed.

## Regression protection

CI now fails if the adapter ever uses the invalid bare `LIGHT_BRIGHTNESS_TARGET = ...` command parameter again.

## Compatibility

- Minimum Director OS: **3.3.0**
- Production PWA: **https://app.c4bridge.io**
- LAN API port: **41999**
- Control4 driver metadata version: **4**

## Test

Update the existing C4Bridge driver to alpha.4, connect the PWA, and test one visible light first.

Expected Composer properties:

- Bridge Version: `0.1.0-alpha.4`
- Status: `Ready (light adapter initialized)`
- API Status: `Online - light control alpha`
