# DirectorLink v1.0.0

**Direct to Director. End-to-end integration. Open source.**

DirectorLink 1.0: the app's key no longer crosses your home network, and a round of security fixes from a public review of the code (issue #43; thanks to @YehudaEi).

## Sealed at home, too

- **Requests at home are sealed.** Until now the app used its key openly on the home network, while everything through the cloud was sealed end to end. It now seals every request at home as well, with the same lock, so someone on your Wi-Fi (a guest, a hacked gadget) cannot pick up the key and take over the home.
- **Pairing with a key exchange.** When you pair, the app and the controller agree on a secret the network never sees, and the new key comes back sealed with it and the pairing code. Browsers without this feature, and scripts, pair as before.
- **Once sealed, never in the clear.** As soon as your controller has answered one sealed request, the app never sends it the key openly again, whatever answers on the network.
- **Pairing only at home.** A pairing code can no longer be tried through the cloud. Five wrong codes lock pairing for that device for a minute (not for everyone), and twenty wrong codes close the code: make a new one in Composer.
- **Only DirectorLink's sites.** Browsers may reach the controller only from app.directorlink.io and console.directorlink.io; `localhost` is refused. Requests must name the controller by its address or a local name (such as `director.local`), which stops a web page from reaching it through a name it controls (DNS rebinding).

Scripts and the API console can keep using `Authorization: Bearer` on the home network.

## Invitations and accounts

- **The controller registers its own invitations.** When an admin invites someone, the controller tells DirectorLink's servers which email the invitation is for, over its own connection. Other members can no longer register invitations for the home.
- **Sign out everywhere** (Settings → Account): ends your account's sessions on every device, for a lost phone or a shared computer, and says so only once it has.
- Expired sessions are deleted every day.

## For installers

- **If a copy of the project's data got into the wrong hands:** run **Revoke All API Keys**, and have the home's owner tap **Replace the remote secret** in the app (Settings → Account, at home). The controller makes the new secret and DirectorLink's servers take it only from the owner, so whoever holds the copy cannot do it first.
- **Reset Remote Identity** (a new Composer action), the last resort: the controller becomes a new home for DirectorLink's servers; the owner links it again and invites everyone again.
- The home's location (for sunrise, sunset and the weather) is shown only to admins, rounded to about a kilometre.
- Every secret the driver makes (keys, codes, invitation links, the home secret) now comes from its own random pool, fed by the controller's random ids, clocks and, where the controller allows it, the system's random source, instead of from one source alone.

## Behind the scenes

- The build and release actions are pinned to exact versions, and Dependabot keeps them current.
- The repository check refuses local tool settings and secret files. A local settings file committed by mistake in 0.3.0 was removed from the whole history.

## Installing

Update DirectorLink in Composer (it loads without a reboot; keys, scenes and schedules stay). The app updates by itself. Keys paired before 1.0.0 keep working and are sealed from now on; if you think a key was picked up on your network before, revoke it and pair again.

Going back to 0.15.0 keeps keys, scenes and schedules, but an app that has sealed with the controller then refuses to send it its key: pair that device again.

## Known issues

- Someone who can change traffic on your home network during pairing (not only listen) could still take that key; pair on a network you trust. Local HTTPS would close this.
- The size of a sealed message still shows roughly what it is (a camera picture or a command).
- The API console (console.directorlink.io) still sends its key openly on the home network: use it on a network you trust.
- A Composer schedule and a DirectorLink schedule that act on the same device both run; DirectorLink does not read Composer programming.
- Only relay 1 of each KNX Contact/Relay device is controlled; KNX percentage dimming remains deferred (issue #11).
