# DirectorLink v1.13.1

**Direct to Director. End-to-end integration. Open source.**

Only Control4's documented driver API.

DirectorLink is an independent project, not affiliated with Control4 or Snap One.

## Only Control4's documented driver API

A review checked every call the driver makes to Control4 against Snap One's public DriverWorks API reference, and found two things outside it, both fixed now. The driver no longer reads `/dev/urandom` itself: its secrets come from Director's own random UUIDs, which the reference says draw on the operating system's randomness, mixed as before with the clock and the times requests arrive. And it now listens only for the project changes the reference documents: a device added, removed or renamed, and Refresh Navigators, no longer Director's internal events for a device moved, a driver added and a project loaded. A new driver still shows within seconds (its devices are added), and a project loaded starts the driver again. The build now fails if the driver ever names a Control4 function that is not in the reference, or reads a file (ADR-088).

A device moved to another room shows after Refresh Project (Composer → DirectorLink → Actions) or the next automatic read.

## Installing

- **Update DirectorLink in Composer** as usual. The app updates by itself. The cloud is unchanged; no D1 migration.
- **Going back to 1.13.0:** nothing is lost; nothing stored changes.

## For developers

- The DirectorLink log's *watching the project for Composer changes* lists four events (`OnItemAdded, OnItemRemoved, OnItemNameChanged, OnPIP`) and says `device_moved` "shows after Refresh Project".
- `scripts/check_package.py` keeps a list of the 46 Control4 functions the driver uses, each with its page in the reference (`DOCUMENTED_C4`). No API change.
