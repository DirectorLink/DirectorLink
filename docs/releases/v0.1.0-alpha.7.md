# C4Bridge v0.1.0-alpha.7

KNX dimmer compatibility build based on the alpha.6 Director snapshot.

## What alpha.6 proved

The full path is working:

```text
app.c4bridge.io
  -> C4Bridge HTTP API
  -> C4:SendToDevice
  -> Light V2 proxy
  -> KNX dimmer driver
  -> KNX Tunneling Gateway
```

The snapshot captured C4Bridge sending:

```text
SET_BRIGHTNESS_TARGET
PERCENT = 48
```

and Director immediately sending a KNX gateway payload.

However, the Control4 app sends its command through Director's broker as XML `type="number"`, while DriverWorks `C4:SendToDevice` serialized C4Bridge's value as `type="INT"`. The physical KNX dimmer did not react to the C4Bridge path.

## alpha.7 KNX compatibility path

For Light V2 proxies backed by `knx_dimmer.c4i`, explicit brightness now uses Control4's documented DriverWorks light command:

```text
RAMP_TO_LEVEL
LEVEL = 0..100
TIME = 0
```

Other Light V2 dimmers retain the existing `SET_BRIGHTNESS_TARGET / PERCENT` path.

On/Off is unchanged because it is already validated on the real system.

## KNX brightness feedback

The snapshot also showed that these KNX dimmers do not update Light V2 variable 1001 after percentage changes from the Control4 app. They report brightness again on certain state transitions such as a full On.

C4Bridge therefore advertises `brightness_feedback=false` for `knx_dimmer.c4i` backed lights. The PWA no longer reports a false failure after five seconds when a KNX brightness command was dispatched successfully.

## Test

1. Update the existing C4Bridge instance to alpha.7.
2. Confirm On/Off still works.
3. Set a KNX dimmer to 30%.
4. Confirm the physical light changes.
5. Set it to 70%.
6. Confirm the physical light changes again.

The PWA will show that the brightness command was sent and that level feedback is unavailable for this KNX driver.
